### D1 — Monday: daily and weekly fire in the same minute; `/api/v1/briefs/latest` is non-deterministic
On the default schedule (`0 9 * * 1-5`) the weekly spec is `0 9 * * 1`. robfig/cron runs each entry in its own goroutine (`cron.go:startJob`), so on Monday `runBrief` and `runWeekly` run concurrently. Consequence: two Telegram/Slack messages at 09:00, and two `brief_payloads` rows with `generated_at` milliseconds apart. `ListBriefPayloads` orders by `generated_at DESC, id DESC`, so `GET /api/v1/briefs/latest` returns whichever stored last — the console bell and a future share link cannot rely on it to be the weekly. `GET /api/v1/briefs` has no `kind` filter and `brief_payloads` has no `kind` column, so the console must parse every payload to find the weekly. What should change: add a `kind` column on `brief_payloads` (written from `StructuredBrief.Kind`) and accept `?kind=daily|weekly` on both routes; decide whether Monday sends one combined message or two.

### D2 — `merged_count` is 0 for task families autopilot never tracks
`merged` events are written only by autopilot (`internal/autopilot/controller.go:10726`, stage transitions) and heal paths. Per the recorded pitfall (PR#4992 / pilot#4999), only `pilot/GH-*` PRs enter `activePRs`; Jira/Linear PRs and tenants with autopilot disabled never get a `merged` event. Consequence: `merged_count` reads 0 on those tenants while `tickets_shipped` is non-zero — the proof line contradicts itself. Also, `runner.go:2717` and the GH-4292/GH-4368 heals stamp `merged` at heal time, so a heal sweep can count old merges in the current week. What should change: state the limitation in the FEATURE-MATRIX row now; when the external-merge/Jira leg (pilot#4999) lands, no code change is needed here.
